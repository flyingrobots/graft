# Graft v0.14.0

Graft now limits its shared daemon graph pool to four resident handles by
default. Idle sessions keep their workspace identities without keeping every
graph they have used in memory.

## What changes

A request reuses its resident graph when available. If another graph needs a
slot, the pool evicts the least recently used idle handle. Running operations
hold leases that protect their graphs until settlement. Eviction preserves
durable index data, and subsequent operations can reopen it.

`GRAFT_WARP_MAX_RESIDENTS` accepts an integer from 1 through 64. The count
includes opens in progress and separate repository/writer lanes. Status adds
`activeWarpResidents`; it is distinct from unique repository count.

Daemon cleanup now attempts every owned stage before reporting aggregate
failures. Failed construction and initial requests retire their sessions,
signal shutdown reports failures, and cross-repository rebind preserves its
history even with a single resident slot.

## Compatibility and upgrade

The documented root exports and command names are unchanged. This pre-1.0
minor release changes capacity behavior: when every slot is pinned, a request
for another lane fails rather than opening beyond the bound. Retry after an
operation settles, or choose a larger finite limit for the workload.

Install `@flyingrobots/graft@0.14.0` and restart the daemon to load it. Existing
MCP clients may need to reconnect because transport sessions end on restart.
Consumers of daemon status must accept the added `activeWarpResidents` field.

The limit bounds handles in this pool. It does not bound the bytes in one
graph, worker-process memory, or total RSS. Cache recency does not establish
source freshness. The memory investigation did not conclusively attribute
the earlier reported 7 GB incident.
