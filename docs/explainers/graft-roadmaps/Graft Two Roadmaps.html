An architecture map, not a status memo

Graft has two roadmaps because it is solving two different-sized problems.

The short road makes one real Graft operation causal through Edict and Echo. The long road turns that substrate into a safe daemon-managed product across workspaces, caches, history, policy, and rollout. They overlap, but neither can honestly stand in for the other.

01 · One request to carry through the whole story

Start with file_outline, because the abstraction only matters if a real tool crosses it.

A request for the outline of src/mcp/server.ts already returns useful, structured data. The architectural gap is not the parser or the output; it is the authority and causal history of the bytes being parsed. Following this one call exposes exactly what #228 changes and why the larger managed roadmap still remains afterward.

02 · The cast and the mental model

Five components play different roles; confusing their ownership created most of the roadmap ambiguity.

Graft owns the user-facing code intelligence and its structural semantics. Edict declares operations. Echo retains and replays causal execution. The daemon supplies product-level authorization and workspace management. git-warp is the current legacy history provider. Once those ownership lines are explicit, the two roadmaps stop looking redundant.

01

Graft

Context governor and structural-analysis application. It owns file_outline, receipts, policies, and the meaning of structural facts.

02

Edict

Source language and compiler path for declaring the operation. #228 requires Graft-owned ObserveWorkspaceSnapshot source, not a native callback.

03

Echo

Causal runtime and retained history. It admits request and settlement, writes durable order, recovers after restart, and supports closed-world replay.

04

Managed daemon

Long-lived product control plane for sessions, grants, workspace identities, caches, bindings, lifecycle, hooks, and rollout.

05

git-warp

Current committed-history substrate. The intended future posture is explicit import or fallback evidence, never silent semantic authority.

SEAM

AdmittedWorkspaceReadView

The landed inner boundary. It lets Graft parse immutable admitted bytes, but it does not itself observe, settle, retain, or recover those bytes.

The authority seam is the most important foil. A type named “admitted” can make the architecture look farther along than production composition is. The source explicitly says the settled side is not yet produced in production and that #228 must build the decoder.

The inner chamber is built. #228 installs the causal plumbing that can lawfully fill it.

In summary, the components are not competing implementations of one thing. They form a stack of semantic ownership, declared effects, causal retention, managed authority, and legacy compatibility—and each roadmap cuts through that stack at a different altitude.

03 · Why two roadmaps exist

One roadmap proves the substrate transition; the other sequences the product that will depend on it.

The Echo campaign asks, “Can one real Graft operation be requested, observed, settled, analyzed, recovered, and replayed causally?” The managed-workspace roadmap asks, “How does a daemon safely expose many workspaces and durable features to users?” Those questions share a future history provider, but they have different acceptance gates and different sources of dependency truth.

05 · Where planning claims diverge from executable reality

The architecture is clearer than the tracker, so status must be read from several evidence surfaces.

Graft's documents, issues, milestones, and source code each answer a different question. Drift appears when one is read as authority for another. The table keeps those gaps visible instead of silently normalizing them into an overconfident percentage.

06 · How this map was audited

The graph was reconstructed from source, planning documents, and live dependency endpoints—and the dead ends changed the conclusion.

The audit began with repository direction, then checked code and branch state, enumerated milestones and issues, and finally queried native blocked-by and blocking relationships. Two tempting shortcuts failed: milestone aggregates did not enumerate cleanly, and old issue prose disagreed with the newer design. Keeping those failures is part of the evidence.

  1. 01

    Recover execution gravity

    Read BEARING.md, METHOD, the #228 packet, and the G0-G12 roadmap before interpreting issue names.

  2. 02

    Inspect implemented composition

    Confirmed the admitted read seam and the production LiveWorkspaceReadSource construction in source.

  3. 03

    Enumerate the trackers

    Mapped 105 managed task issues (#97–#201), 15 formal milestones, and the seven Graft issues in the Echo transition.

  4. 04

    Query native edges directly

    Used GitHub's dependency endpoints for every Echo issue instead of inferring arrows from prose.

  5. 05

    Preserve drift

    Marked G0, G1, #228, and milestone-count discrepancies as claims gaps instead of “fixing” the graph to look tidy.

Dead end A

Milestone aggregate ≠ issue enumeration

The Echo-native milestone reports five open items, while direct enumeration yields #230 and #231. The site trusts enumerated nodes and displays the aggregate as drift.

Dead end B

Issue body ≠ latest protocol

#228's “expected basis” language would reintroduce a pre-observation read. The newer packet's unknown-basis decision takes precedence.

Boundary

Documented edge ≠ native blocker

The #231-to-G6 convergence is architecturally meaningful but not mechanically enforced in GitHub, so it stays dashed.

In summary, the map is reproducible because each arrow has provenance and each discrepancy remains visible. A future refresh can change status without rewriting the meaning of an edge.

07 · What mature looks like

Maturity is reached when causal proof and product governance meet without a fallback-shaped hole between them.

“Done” is not merely merging #228, nor is it closing 105 issues. The causal road must prove retained request, settlement, recovery, and zero-read replay; the product road must then expose safe multi-workspace reads, scoped derived state, managed history, truthful queries, lifecycle controls, and a reversible daemon-first rollout.
